## Story 10: Temporal Database Schema & Storage Layer

**Objective**: Create the SQLite (default) / PostgreSQL (optional) schema for `temporal_events` and `temporal_journal` tables with agent-scoped access.

**Files to create:**
```
src/parousia/temporal/
  __init__.py
  db.py              # Schema creation, connection management, migrations
tests/
  test_temporal_db.py
```

**What to build:**
- `TemporalDB` class with `connect()`, `create_tables()`, `close()`
- SQLite path: `/var/lib/parousia/temporal.db` (configurable via `temporal.db.path`)
- PostgreSQL: `temporal.db.postgres_url` in config, `psycopg2` optional dependency
- `temporal_events` table: id, agent_id, title, start_time, end_time, flexibility, event_type, status, source, stakeholders, metadata, created_at, updated_at
- `temporal_journal` table: id, agent_id, title, description, entry_type, occurred_at, tags, metadata, created_at
- Indexes: `idx_events_agent_time` on (agent_id, start_time); `idx_journal_agent_time` on (agent_id, occurred_at)
- WAL mode for SQLite (concurrent read safety)
- Agent-scoped query methods: `get_events(agent_id, start_range, end_range)`, `get_journal(agent_id, limit=5)`
- Migration: `setup()` checks if tables exist, creates if missing (idempotent)

**Verification:**
- `TemporalDB().create_tables()` creates both tables in `:memory:` SQLite
- Insert event for agent A → `get_events("B")` returns empty (agent isolation)
- SQLite WAL mode confirmed via `PRAGMA journal_mode`
- PostgreSQL path: `TemporalDB(postgres_url="...")` connects and creates tables
- `setup()` called twice → no error, no duplicate tables

## Story 11: Temporal DSL Serializer

**Objective**: Convert DB rows into the token-lean DSL text format for LLM context injection.

**Files to create:**
```
src/parousia/temporal/
  serializer.py       # to_dsl(agent_id, mode) → string
tests/
  test_serializer.py
  fixtures/
    sample_events.json
```

**What to build:**
- `TemporalSerializer` class initialized with `TemporalDB` instance
- `to_dsl(agent_id, mode="standard")` method returns the DSL string
- Mode configurations from config: `standard` (past 1d/future 3d), `planning` (future 14d), `retrospective` (past 7d), `full` (past 30d/future 30d)
- Format:
  ```
  !NOW: 2026-06-14 W24 Sun 14:30 | DOMAIN: GENERAL_CORP
  #PAST_WINDOW (3d)
  - MM-DD HH:MM|HH:MM [id:eN] Title *DONE
  #PLANNED_WINDOW (7d)
  - MM-DD HH:MM|HH:MM [id:eN] [F:flex] Title
  #TIMERS_ALARMS
  - T: Xm remaining [id:tN] Title
  - A: MM-DD HH:MM [id:aN] Title
  #JOURNAL (recent)
  - MM-DD [id:jN] Title
  ```
- Empty sections omitted entirely
- Completed events >1 day past excluded from non-retrospective modes
- Journal: last 5 entries in standard/retrospective modes
- Flexibility `[F:high/low/none]` only on future events
- `measure_tokens(dsl_string)` — rough token count (chars/4)
- Year format: `MM-DD` for current year, `YYYY-MM-DD` for different years

**Verification:**
- Empty agent → `!NOW` header only, no empty sections
- 15 events in standard mode → <200 tokens
- Planning mode → only future events, no past window
- Retrospective mode → only past events with `*DONE`, includes journal
- Timer vs alarm distinction: `T:` vs `A:` prefix
- Journal entries appear in order, most recent first, with `[id:jN]`

## Story 12: MCP Temporal Tools

**Objective**: Add `get_temporal_context`, `schedule_event`, `cancel_event`, `set_timer_alarm`, `nominate_milestone` tools to the existing MCP server on port 8081.

**Files to create/modify:**
```
src/parousia/guard/
  mcp_server.py       # MODIFY: add 5 new tools to existing server
src/parousia/temporal/
  tools.py            # Tool handler implementations
tests/
  test_mcp_temporal.py
```

**What to build:**

Five tools registered on the existing `Server("parousia-guard-mcp")`:

1. **`get_temporal_context(mode, agent_id)`** — calls `TemporalSerializer.to_dsl()`, returns `{context, mode, event_count, conflicts, consideration}`. `consideration` field present only when opportunistic injector is active.

2. **`schedule_event(title, start_time, end_time, flexibility, stakeholders, metadata)`** — inserts into `temporal_events`. Detects time-range overlaps (conflicts). Generates export payloads (`.ics`, Google, MS Graph). Returns `{scheduled, event_id, conflicts, export_formats}`.

3. **`cancel_event(event_id)`** — sets `status='cancelled'` on event row. Returns `{cancelled, event_id, title}`.

4. **`set_timer_alarm(title, duration_minutes?, trigger_at?)`** — inserts timer/alarm event. Validates exactly one of duration/trigger_at. Returns `{set, alarm_id, type, remaining_seconds}`.

5. **`nominate_milestone(title, description, entry_type, occurred_at, tags)`** — inserts into `temporal_journal`. Returns `{recorded, journal_id, title}`.

**Integration:**
- `handle_list_tools()` returns union of email + temporal tools (6 total)
- `handle_call_tool()` dispatches by `name`
- `agent_id` resolution: check `X-Agent-ID` header or MCP session metadata, fallback to first config agent
- TemporalDB initialized at server startup alongside Redis/RateLimiter
- No rate limiting on temporal tools

**Verification:**
- MCP client connects, discovers all 6 tools (send_email + 5 temporal)
- `get_temporal_context("standard")` returns valid DSL string
- `schedule_event` inserts row, returns event_id and export payloads
- `schedule_event` with overlap → conflicts array returned
- `cancel_event("e3")` → status='cancelled', row persists
- `set_timer_alarm` with no duration or trigger_at → error
- `set_timer_alarm` with both duration and trigger_at → error
- `nominate_milestone` → journal entry created, confirmed in `get_temporal_context`
- Agent isolation: agent A's events invisible to agent B's `get_temporal_context`

## Story 13: Temporal Ingest Pipeline

**Objective**: Parse `.ics` files, structured JSON, and unstructured text into temporal events. Bridge email `.ics` attachments to temporal ingest.

**Files to create/modify:**
```
src/parousia/temporal/
  ingest.py           # .ics parser, JSON validator, NL passthrough
src/parousia/guard/
  ingest.py           # MODIFY: detect .ics MIME parts, route to temporal
tests/
  test_temporal_ingest.py
  fixtures/
    sample.ics
    sample_recurring.ics
    sample_timezone.ics
    broken.ics
```

**What to build:**

*`.ics Parser (`TemporalIngest.parse_ics(ics_text, agent_id)`):*
- Parse `VEVENT`, `VTODO`, `VALARM` components using `icalendar` library
- Extract: `SUMMARY`→title, `DTSTART`/`DTEND`→start/end, `ORGANIZER`/`ATTENDEE`→stakeholders, `UID`→metadata.uid
- `RRULE`: store recurrence rule in `metadata.rrule` string; do NOT expand (expansion at query time)
- Timezone: convert to UTC, store original TZID in `metadata.tzid`
- Idempotent: check `metadata.uid` before insert, skip duplicates
- Return list of created `event_id`s

*Structured JSON Ingest (`TemporalIngest.parse_json(payload, agent_id)`):*
- Validate required fields: `title`, `start_time`
- Optional: `end_time`, `flexibility`, `stakeholders`, `metadata`
- Insert into `temporal_events`, return `event_id`

*Unstructured Text (`TemporalIngest.parse_nl(text, agent_id, llm_endpoint=None)`):*
- If `llm_endpoint` set: POST text → receive structured response, insert
- If `llm_endpoint` unset: return passthrough dict (agent handles it)
- LLM call timeout: 5s, fire-and-forget, fallback to passthrough on failure

*Email Bridge (modify `src/parousia/guard/ingest.py`):*
- After MIME parsing in Phase 1, check for `Content-Type: text/calendar` or `.ics` file attachment
- If found: extract `.ics` content, call `TemporalIngest.parse_ics()`, attach result to agent webhook payload
- If `.ics` parsing fails: still deliver the email to the agent, include parse error in payload

*REST Endpoint (add to existing FastAPI server):*
- `POST /temporal/ingest` — accepts JSON, calls `TemporalIngest.parse_json()`, returns `{event_id}`
- Requires `agent_id` in payload (reject 400 if missing)

**Verification:**
- `parse_ics(sample.ics)` → correct title, start, end, UID stored
- `parse_ics(recurring.ics)` → RRULE in metadata, single event row stored
- `parse_ics(timezone.ics)` → UTC conversion correct, original TZID preserved
- `parse_ics(broken.ics)` → graceful failure, error returned
- `parse_json(valid_payload)` → event_id returned, row in DB
- `parse_json(missing_agent_id)` → ValueError
- `parse_nl("coffee tomorrow 2pm", llm_endpoint=None)` → passthrough dict
- Email with `.ics` attachment → parsed events attached to webhook payload
- Email with broken `.ics` → email still delivered, parse error noted
- Duplicate `.ics` (same UID) → 200, existing event_id, no duplicate row

## Story 14: Translation Layer (Outbound Export)

**Objective**: Generate `.ics`, Google Calendar JSON, and MS Graph JSON payloads for events.

**Files to create:**
```
src/parousia/temporal/
  export.py           # to_ics(), to_google_json(), to_msgraph_json()
tests/
  test_temporal_export.py
```

**What to build:**

- `TemporalExport` class with three methods:

1. **`to_ics(event_row)`** — returns RFC 5545 iCalendar string
   - `VEVENT` with `UID`, `DTSTART`, `DTEND`, `SUMMARY`, `DESCRIPTION`, `ORGANIZER`/`ATTENDEE`
   - DateTime in UTC with `Z` suffix
   - Validated: round-trip parseable by `icalendar`

2. **`to_google_json(event_row)`** — returns Google Calendar API v3 `events.insert()` body
   - `{summary, start: {dateTime, timeZone}, end: {dateTime, timeZone}, description, attendees: [{email}]}`
   - Timezone from metadata.tzid or "UTC"

3. **`to_msgraph_json(event_row)`** — returns Microsoft Graph `POST /me/events` body
   - `{subject, start: {dateTime, timeZone}, end: {dateTime, timeZone}, body: {contentType: "text", content}, attendees: [{emailAddress: {address}}]}`

- `to_all_formats(event_row)` → `{ics, google, msgraph}` dict
- These are pure functions — no API calls, just JSON construction

**Integration with US-12:**
- `schedule_event` tool calls `to_all_formats()` and includes in response
- `get_temporal_context` includes `export_formats` when mode is `planning`

**Verification:**
- `to_ics(event)` → valid RFC 5545, reparsed by `icalendar` without error
- `to_ics(event)` includes UID, SUMMARY, DTSTART, DTEND
- `to_google_json(event)` matches Google Calendar API v3 event schema
- `to_msgraph_json(event)` matches MS Graph event schema
- Stakeholders mapped to Google `attendees[].email` format
- Stakeholders mapped to MS Graph `attendees[].emailAddress.address` format

## Story 15: Opportunistic Temporal Injection

**Objective**: Lightweight keyword classifier and consideration hints on MCP tool returns.

**Files to create:**
```
src/parousia/temporal/
  injector.py         # temporal_relevant(), get_consideration_hint()
tests/
  test_temporal_injector.py
```

**What to build:**

*Keyword Classifier:*
- `temporal_relevant(text: str, keywords: list[str] | None = None) -> bool`
- Default keywords from config: `schedule, calendar, meeting, appointment, event, next week, tomorrow, yesterday, remind, deadline, due date, upcoming, this month, timeline, agenda, invite, rsvp`
- Case-insensitive substring match
- Returns True if ≥1 keyword found, False otherwise
- Sub-millisecond performance (compiled regex or `any(k in text.lower())`)

*Consideration Hints:*
- `get_consideration_hint(tool_name: str, tool_result: dict) -> str | None`
- Context-aware hint generation:
  - `send_email` succeeded + body has temporal keyword → "This email mentions a deadline. Your temporal context may be relevant."
  - `get_temporal_context` → "You have {count} upcoming events in the next 24 hours."
  - `schedule_event` succeeded → "Event scheduled. You have {remaining_slots} open slots this week."
  - Nomination pulse → "It's been {days} days since your last temporal milestone review."
- Hints never exceed 120 characters
- Returns `None` when no hint applicable

*Config integration:*
- `temporal.opportunistic.enabled: true/false` — master switch
- `temporal.injection_keywords: [...]` — customizable keyword list
- When disabled, `temporal_relevant()` always returns False, `get_consideration_hint()` always returns None

*Integration:*
- `get_temporal_context` tool in US-12 calls `get_consideration_hint()` for its response
- MCP `send_email` tool (Phase 1) modified to include consideration hint from `get_consideration_hint("send_email", result)`

**Verification:**
- "schedule a meeting tomorrow" → True
- "what's the weather like" → False
- "deadline approaching" → True
- "meeting" in "Let's arrange a meeting" → True
- Empty string → False
- Custom keywords from config respected
- `send_email` with temporal keyword → consideration hint present
- `cancel_event` tool → no consideration hint (deterministic tool)
- Hint length never exceeds 120 chars
- When `opportunistic.enabled: false` → all functions return False/None

## Story 16: Temporal Journal & Monthly Nomination Pulse

**Objective**: Journal entry storage (separate from calendar) + Parousia-side monthly cron that prompts the agent to nominate milestones.

**Files to create:**
```
src/parousia/temporal/
  journal.py          # JournalEntry CRUD, pulse generation
  pulse.py            # Pulse sender (cron trigger)
tests/
  test_temporal_journal.py
  test_temporal_pulse.py
```

**What to build:**

*Journal CRUD (`JournalManager`):*
- `add_entry(agent_id, title, description, entry_type, occurred_at, tags)` → `journal_id`
- `get_recent(agent_id, limit=5)` → list of entries, most recent first
- `count_entries(agent_id)` → int
- `days_since_last(agent_id)` → days since most recent journal entry
- Entries are immutable — no update/delete via public API

*Pulse Generator:*
- `generate_pulse_prompt(agent_id)` → string
- Template from config: `temporal.pulse.prompt_template`
- Variables: `{days_since_last}`, `{event_count}`, `{journal_count}`
- `send_pulse(agent_id, webhook_url, dry_run=False)` → POSTs prompt to agent webhook
- Dry run: returns prompt text, does not POST

*Cron Integration:*
- `parousia-guard temporal setup --pulse` installs a systemd timer or crontab entry
- First pulse fires immediately on setup ("initialization")
- Schedule from config: `temporal.pulse.schedule` (default: `0 9 1 * *`)
- `parousia-guard temporal pulse --agent-id hermes` for manual trigger

**Verification:**
- `add_entry()` → journal_id returned, row in DB
- `get_recent(limit=5)` → correct ordering, most recent first
- `days_since_last()` → correct delta when entry exists, `None` when empty
- `generate_pulse_prompt()` → template vars substituted correctly
- `send_pulse(dry_run=True)` → prompt printed, no POST
- Journal entries appear in DSL `#JOURNAL` section via US-11 serializer
- Nomination pulse webhook timeout handled (queue + retry, same as Phase 1 email queue)


**What to build:**

Click command group `parousia-guard temporal`:

| Command | Flags | Action |
|---------|-------|--------|
| `setup` | `--pg URL`, `--pulse`, `--force` | Initialize DB, create tables, install pulse cron |
| `validate` | `--agent-id ID` | Check DB connectivity, schema, serializer output |
| `status` | `--agent-id ID`, `--json` | Event counts, DB size, last pulse, journal stats |
| `export` | `--format ics/google/msgraph`, `--event-id ID`, `--output PATH` | Export event(s) to format |

| `pulse` | `--agent-id ID`, `--dry-run` | Send nomination pulse |
| `db` | `--stats`, `--vacuum` | DB management |

**Implementation:**
- All commands use the shared `load_config()` pattern from Phase 1
- `setup` is idempotent — safe to run multiple times
- `validate` exits 0 on healthy, non-zero on failures with specific messages
- `status --json` outputs machine-readable JSON
- All commands respect `--config` flag

**Verification:**
- `parousia-guard temporal setup` → DB file created, tables exist
- `parousia-guard temporal setup` (second run) → no error
- `parousia-guard temporal validate` → exit 0 on clean system
- `parousia-guard temporal validate` with no DB → exit 1, message: "Database not found"
- `parousia-guard temporal status --json` → valid JSON with event_count, journal_count
- `parousia-guard temporal export --format ics --event-id e1` → valid .ics to stdout
- `parousia-guard temporal ingest --ics sample.ics --agent-id hermes` → event_id printed
- `parousia-guard temporal pulse --agent-id hermes --dry-run` → prompt printed, no POST
- `parousia-guard temporal db --stats` → table sizes, row counts
